# SpacetimeDB 2.12: what is new, and what we should do (task #94230)

Dated snapshot, 2026-10-18. We pin `spacetimedb = "2.10"` (module) and `spacetimedb-sdk = "2.10.1"`; the local CLI is 2.10.1.

## What changed from 2.10 to 2.12

- **2.12.0 (Oct 13):** unit testing for Rust and TypeScript modules against an in-memory datastore, no server (`spacetimedb::test_utils`, feature `test-utils`). Typed persistent env vars (`spacetime env`). TypeScript/C# SDK auto-reconnect (Rust planned). HS256 JWTs no longer accepted. Fix for duplicate interval-scheduled reducer calls. Rollback-safe system-table additions.
- **2.11.0:** `spacetime describe` prints the schema.
- **2.10.2:** non-default sequence parameters rejected at validation; non-transactional sequence state removed.
- **2.10.1:** scheduled reducers now run concurrently; already-expired ones are no longer in strict `scheduled_at` order.

## Unit tests in the module: what the API gives

- `TestContext::new()` builds an in-memory datastore from the `#[table]`s in the test binary.
- `ctx.with_reducer_tx(TestAuth::internal(), |rctx| ...)` hands the body a real `&ReducerContext`. It commits on `Ok`, rolls back on `Err` or panic.
- `TestClock` (`advance`) and `TestRng` give deterministic time and randomness. Procedure and view contexts exist too.

This answers the user's question: yes, reducer tests can move into the module crate. Our module tests say "a unit test cannot build a `ReducerContext`" (`spacetime/module/src/tests.rs`). That is no longer true.

## Spike 2 result: it works (supersedes "blocked" below)

A second round of spikes got the in-memory store running with our real reducers. Three fixes were needed:

1. **Cap the ICU family.** `temporal_rs 0.1.2` needs `icu_calendar`/`icu_locale` 2.1.x, but the resolver picks 2.3.x. Declaring `icu_calendar = "~2.1"` and `icu_locale = "~2.1"` as direct dependencies of the test crate fixes it. Drop them once upstream moves.
2. **Use a separate test crate.** The module is `cdylib` + `rlib`, and V8 cannot link into a shared object (`R_X86_64_TPOFF32` linker error). Even a path dependency fails, because cargo builds every crate type. The test crate compiles the module's own `src/lib.rs` as a plain rlib:
   ```toml
   [package]
   name = "dispatch-spacetime-module-tests"
   edition = "2021"
   [workspace]
   [lib]
   name = "dispatch_spacetime_module"
   path = "../module/src/lib.rs"
   [dependencies]
   spacetimedb = { version = "2.12", features = ["test-utils"] }
   chrono = { version = "0.4", default-features = false }
   icu_calendar = "~2.1"
   icu_locale = "~2.1"
   ```
   The module's existing 191 unit tests ran green inside this crate too. The wasm build of the module stays untouched.
3. **Build environment:** `gcc-c++` and `OPENSSL_NO_VENDOR=1` with system `openssl-devel`.

Two tests in `tests/` of that crate passed, using only the public reducers:
- `create_task`, then `delete_task` on a not-done task returns `Err`.
- `register_host`, `create_task`, `request_dispatch`; advance `TestClock`; call `expire_dispatch_request` with the timer row; the request ends `failed`. The in-memory host does not fire scheduled reducers itself, so the test calls the reducer, as the live host would. An internal-auth call passes the module's own-scheduler check.

Costs: the new crate has its own `Cargo.lock` (about 6400 lines), a first build of several minutes, and about 6.4 GB in `target/`. A warm re-run takes under a second. Tests in `tests/` see only `pub` items (`pub(crate)` helpers such as `create_dispatch_request` are out of reach there). They go through the reducers, which is the point.

The wiring work remains: a script like `check-spacetime-module.sh` for the new crate, CI and pre-push hook entries (they need the two build-environment items above), the source-hash stamp for `module.wasm`, and the docs checkers. That is a task of its own.

## Spike 1 result: blocked (first attempt, kept for the record)

A spike added `spacetimedb = { version = "2.12", features = ["test-utils"] }` as a dev-dependency and one reducer test. It did not build:

1. `test-utils` links `spacetimedb-core` and the `v8` engine. The module's `Cargo.lock` grew by about 6000 lines.
2. It needs `OPENSSL_NO_VENDOR=1` (or `perl-FindBin`) and a C++ compiler (`gcc-c++`, which was missing here; I installed it). CI images need the same.
3. Then `temporal_rs 0.1.2` fails to compile against `icu_calendar 2.3.0` (`AnyCalendarDifferenceError` missing). Pinning `icu_calendar` to 2.1.1 conflicts with `icu_locale`. This is an upstream dependency conflict; not resolved.

I reverted the spike. Nothing in the tree changed except this note.

## Recommendations

1. **Adopt the in-memory store through a separate test crate** (recipe in "Spike 2 result"). The "blocked" findings below are superseded: the ICU cap and the separate crate solve them. Wire it into the check script, CI and the pre-push hook as one task.
2. **If it builds, move these first:** the reducer-level tests now covered only by the live-store tests in `tests/spacetime_module.rs` (create/delete/patch, epic chain, dispatch and session request reducers). Keep the pure-function tests as they are. The scheduled-backstop timers (`expire_dispatch_request`, `expire_session_request`) become testable with `TestClock::advance`; today they are covered only by the in-memory double.
3. **Keep the live-store tests** that check publish and automigration (`tests/spacetime_module.rs`): the in-memory store does not test either. `tests/memory_caller_conformance.rs` stays too until reducer tests cover the same pairs.
4. **Bump to 2.12 as its own change** (module, SDK, CLI pin in CI, regenerate bindings with `./scripts/regenerate-spacetime-bindings.sh`, rebuild `module.wasm`). Check first: do we rely on strict order of expired scheduled reducers (2.10.1)? Do we set non-default sequence parameters (2.10.2)? Do we sign HS256 JWTs (2.12)?
5. **Typed env vars (`spacetime env`)** could hold module settings that now sit in a config table (`config.rs`). Not urgent.
6. **SDK auto-reconnect** is not in the Rust SDK yet. Our own reconnect loop (`src/sync`) stays.
